# Schnorr Implementation Model

This document explains the implementation model shared by the two Schnorr backends and the concrete differences between them.

Backends:
- `src/schnorr_malachite_signer.rs`
- `src/schnorr_num_bigint_dig_signer.rs`
- `src/schnorr_crypto_bigint_signer.rs`

## 1) Shared Model (Both Backends)

## Curve and Key Model

- Both implement secp256k1 arithmetic using curve constants `p`, `n`, and generator `G`.
- Private key validation is strict: `1 <= priv < n`.
- Public key is represented as x-coordinate bytes (`[u8; 32]`) plus reconstructed point.
- Public key normalization uses even-`y` canonicalization:
  - if computed `Y` is odd, backend flips to `p - Y` and adjusts private scalar to `n - d`.

## Signature Primitive

- Signature form is `(r, s)` with fixed serialization `[r(32 LE) || s(32 LE)]`.
- `sign()` and `multi_sign()` both call the same core routine (`sign_common`).
- `verify_signature()` and `verify_multi_signature()` both call `verify_common`.

## Deterministic Nonce and Challenge

- Nonce is deterministic, generated by tagged SHA-256:
  - `tagged_hash("nonce", private_key_bytes, message, counter_bytes)`
  - retries with incrementing `counter` until nonce scalar is non-zero.
- Challenge is also tagged-hash based:
  - `tagged_hash("challenge", r_bytes, public_key_bytes, message) mod n`

## Aggregation Model (Half-Aggregation Style)

- Aggregated signature carries:
  - `count: u16`
  - one combined scalar `s` (32 bytes)
  - per-signer `r` x-coordinates (`count * 32` bytes)
- Fixed serialization header size and bounded count via:
  - `MAX_AGGREGATED_SIGNATURES`
  - `AGGREGATED_SIGNATURE_CONSTANT_SIZE`
  - `AGGREGATED_SIGNATURE_VARIABLE_SIZE`
- Aggregation randomness is deterministic and message-bound:
  - seed from `tagged_hash("aggregate", sum_r_bytes, sum_r_bytes, message)`
  - per-index factor from `tagged_hash("rand", seed, i_bytes, i_bytes)`

## Verification Approach

- Scalar/path bounds are validated (`r < p`, `s < n`).
- Point reconstruction from `r` x-coordinate is validated before use.
- Aggregated verification recomputes per-signer challenge and deterministic per-index random weights.

## 2) Backend-Specific Differences

## Numeric Engine

- `schnorr_malachite_signer`:
  - Uses `malachite_nz::{Integer, Natural}` and malachite modular arithmetic traits.
- `schnorr_num_bigint_dig_signer`:
  - Uses `num_bigint_dig::BigInt` (+ `ModInverse`, `num_traits`).
- `schnorr_crypto_bigint_signer`:
  - Uses `crypto_bigint::U256` (+ modular helper traits) with fixed-width integer arithmetic.

## Byte/Conversion Layer

- Malachite backend uses `to_power_of_2_digits_asc` / `from_power_of_2_digits_asc` conversions.
- Num-bigint backend uses `to_bytes_le` / `from_bytes_le`.
- Crypto-bigint backend uses fixed-size `to_le_bytes` / `from_le_bytes` encoding paths.

## Arithmetic Plumbing

- Both use double-and-add scalar multiplication.
- Both normalize negative modulo results back into field range.
- Both expose equivalent behavior; differences are implementation library APIs and arithmetic helper choices.
- All three expose equivalent behavior; differences are implementation library APIs and arithmetic helper choices.

## 3) Why Two Schnorr Backends Exist

- API compatibility is preserved at trait boundary (`src/lib.rs`).
- Compile-time feature flags allow swapping bigint backend without changing downstream usage.
- This supports MoonBlokz goals from Part VI: replaceability, constrained-target tuning, and verification-oriented optimization choices.

## 4) Invariants to Preserve for Future Changes

- Keep deterministic nonce + challenge tagged-hash flow.
- Keep even-`y` canonicalization behavior consistent.
- Keep serialization layout/stable sizes for `(r,s)` and aggregated signatures.
- Keep aggregation bounded by `MAX_AGGREGATED_SIGNATURES`.
- Keep `sign`/`multi_sign` and verify pairings behaviorally equivalent.
